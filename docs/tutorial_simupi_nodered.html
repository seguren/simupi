¿Qué es SimuPi?

SimuPi es un simulador de Raspberry Pi escrito en Go que genera datos realistas de sensores y simula pines GPIO. Fue diseñado para que puedas desarrollar y probar flujos IoT sin necesidad de hardware físico.

Objetivo del simulador en la materia
En la práctica real usarán una Raspberry Pi 3 con sensores físicos (temperatura, humedad, distancia, etc.) conectada a un broker MQTT. SimuPi reproduce exactamente el mismo protocolo MQTT y la misma API, por lo que los flujos Node-RED que construyan hoy funcionarán sin cambios en el hardware real.

02

Instalación y puesta en marcha

Requisitos previos

  • Go 1.24+ instalado (go.dev/dl)
  • Node-RED instalado (npm install -g --unsafe-perm node-red)
  • Puertos 1883 y 5000 libres en tu máquina

Compilar y ejecutar SimuPi

  1. Clonar (o descomprimir) el repositorio:
    git clone <url-del-repo> simupi-go
cd simupi-go
  2. Compilar el binario:
    go build -o simupi .
  3. Ejecutar:
    ./simupi          # Linux / macOS
simupi.exe        # Windows
  4. Abrir el dashboard en el navegador:
    http://localhost:5000
Tip — Makefile
El proyecto incluye un Makefile. En lugar de los pasos 2 y 3 podés ejecutar directamente make run.

Verificar que todo funciona

En otra terminal, probá el endpoint de salud:

curl http://localhost:5000/api/health
{"status":"ok"}

Si ves {"status":"ok"}, SimuPi está corriendo correctamente.

Iniciar Node-RED

node-red          # abre http://localhost:1880
Atención — Orden de inicio
Siempre iniciar SimuPi antes de Node-RED. El broker MQTT de SimuPi debe estar disponible cuando Node-RED intente conectarse.
03

Interfaz web — Recorrido guiado

Accedé a http://localhost:5000 y verás el dashboard de SimuPi dividido en tres paneles principales.

Panel de GPIO

Hay dos tipos de pines:

TipoDescripciónCómo controlarlo
GPIO Input Simula un sensor digital o botón. Valor: 0 ó 1. Botón Toggle en la UI, API REST, o publicando en MQTT
GPIO Output Simula un actuador (relé, LED, motor). Valor: 0 ó 1. Publicando en MQTT gpio/out/<pin>
Aliasas
Los pines pueden tener nombre amigable. En el escenario Greenhouse, el pin 22 se llama fan y el pin 24 se llama pump. Los alias se muestran en la UI y se pueden usar en los tópicos MQTT.

Panel de sensores

Cada sensor muestra:

  • Valor actual con unidad (ej. 24.53 °C)
  • Modo de simulación (wave, walk, ramp, etc.)
  • Estado de falla — si está activa, aparece stuck u offline
  • Override manual — campo para inyectar un valor específico
  • Gráfico histórico — los últimos 500 valores en tiempo real

Modos de simulación disponibles

ModoComportamientoEjemplo de uso
waveSenoide entre min y max con período configurableTemperatura ambiente día/noche
walkVariación aleatoria ±step desde el valor actualHumedad con fluctuaciones
triangleRampa lineal subida/bajada periódicaNivel de tanque llenándose
sawtoothRampa que sube y vuelve a cero abruptamenteContador de ciclos

Protocolo MQTT — Tópicos y mensajes

SimuPi incluye un broker MQTT embebido en el puerto 1883. No necesitás instalar Mosquitto ni ningún broker externo.

Tópicos publicados por SimuPi (SimuPi → Node-RED)

TópicoPayloadEjemplo
sensor/<nombre> Número flotante como string, 2 decimales "24.53"
gpio/in/<pin> String "0" o "1" "1"

Tópicos suscritos por SimuPi (Node-RED → SimuPi)

TópicoPayloadEfecto
gpio/out/<pin> String "0" o "1" Cambia el estado del GPIO output en el dashboard

Ejemplos de tópicos por escenario

Wildcard MQTT
Para suscribirse a todos los sensores de una vez en Node-RED, usá el tópico sensor/#. El campo msg.topic te dirá cuál sensor envió el mensaje.

API REST de referencia

Todos los endpoints tienen base http://localhost:5000.

MétodoEndpointDescripción
GET /api/health Verificar que SimuPi está corriendo
GET /api/state Estado completo: GPIO, sensores, modos, fallas, aliases
GET /api/scenarios Lista de escenarios disponibles
POST /api/scenarios/load/{nombre} Cargar un escenario (ej. greenhouse)
POST /api/gpio/{pin} Setear pin de entrada. Body: {"value": 1}
POST /api/gpio/{pin}/toggle Invertir valor del pin (0→1 ó 1→0)
POST /api/gpio/{pin}/pulse Pulso HIGH durante N segundos. Body: {"duration": 0.5}
POST /api/sensor/{nombre} Inyectar valor manual. Body: {"value": 25.0}
POST /api/failure/{sensor} Simular falla. Body: {"mode": "stuck"} o {"mode": "offline"}
POST /api/failure/{sensor} Limpiar falla. Body: {"mode": "clear"}
GET /api/history/{sensor} Historial de lecturas (últimas 500)
GET /api/export/{sensor} Descargar historial como CSV
POST /api/config/save/{nombre} Guardar configuración actual como nuevo escenario

Ejemplo con curl

# Inyectar temperatura de 35 °C manualmente
curl -X POST http://localhost:5000/api/sensor/temperature \
     -H "Content-Type: application/json" \
     -d '{"value": 35.0}'

# Simular falla en el sensor de humedad
curl -X POST http://localhost:5000/api/failure/humidity \
     -H "Content-Type: application/json" \
     -d '{"mode": "stuck"}'

# Cargar el escenario Greenhouse
curl -X POST http://localhost:5000/api/scenarios/load/greenhouse

Integración con Node-RED

Configurar el broker MQTT en Node-RED

  1. Abrí Node-RED en http://localhost:1880
  2. Arrastrá un nodo mqtt in al canvas
  3. Hacé doble clic → "Add new mqtt-broker…" → Editar
  4. Completá los campos:
    CampoValor
    Serverlocalhost
    Port1883
    Client IDnodered-simupi (o cualquier nombre)
  5. Click en Add y luego Done

Flujo básico — Leer temperatura y mostrarla

mqtt in
sensor/temperature
→
debug
msg.payload
  1. Arrastrá un nodo mqtt in. Tópico: sensor/temperature
  2. Arrastrá un nodo debug
  3. Conectá la salida del mqtt in a la entrada del debug
  4. Click en Deploy
  5. En el panel de Debug (derecha) verás los valores llegando cada 1 segundo
Convertir el payload a número
SimuPi envía el valor como string ("24.53"). Para operar matemáticamente, usá un nodo function con: msg.payload = parseFloat(msg.payload);

Flujo de control — Activar ventilador según temperatura

mqtt in
sensor/temperature
→
function
parseFloat
→
switch
> 28°C
→
mqtt out
gpio/out/22
  1. Nodo function — convertir y preparar payload: 
    var temp = parseFloat(msg.payload);
msg.payload = temp > 28 ? "1" : "0";

  2. Nodo mqtt out:
    • Tópico: gpio/out/22
    • QoS: 0
    • Broker: el mismo que configuraste antes
  3. Conectar: mqtt in → function → mqtt out
  4. Click en Deploy
  5. En SimuPi, observá el LED del GPIO 22 encenderse cuando temperatura > 28 °C

Ejercicios Prácticos

Ejercicio 1

Control automático de invernadero

Objetivo: Construir un sistema de control para un invernadero que encienda el ventilador cuando la temperatura sea alta y active la bomba de riego cuando la humedad sea baja.
Escenario: Cargar greenhouse en SimuPi.

Especificación del sistema

CondiciónAcción
Temperatura > 28 °CEncender ventilador (GPIO 22 = 1)
Temperatura ≤ 28 °CApagar ventilador (GPIO 22 = 0)
Humedad < 50 %Activar bomba de riego (GPIO 24 = 1)
Humedad ≥ 50 %Apagar bomba de riego (GPIO 24 = 0)

Flujo esperado en Node-RED

sensor/
temperature
→
Lógica
fan
→
gpio/out/22
sensor/
humidity
→
Lógica
pump
→
gpio/out/24

Tareas

  1. Crear el flujo de control descripto arriba.
  2. Agregar nodos debug para registrar cada vez que el ventilador o la bomba cambian de estado.
  3. Usando la API REST, inyectá manualmente temperatura = 35 °C y verificá que el ventilador se encienda. Luego inyectá 20 °C y verificá que se apague.
  4. Exportar el flujo como JSON (Menu → Export → Clipboard) e incluirlo en el informe.

Código de referencia para el nodo function (ventilador)

var temp = parseFloat(msg.payload);
msg.topic = "gpio/out/22";
msg.payload = temp > 28 ? "1" : "0";
return msg;
Consideración de diseño
Con este esquema simple, el sistema envía un mensaje MQTT en cada lectura del sensor aunque el estado no cambie. ¿Cómo podrías modificar el flujo para publicar solo cuando el estado cambia? (Pista: usá context.get() / context.set() en el nodo function).
Ejercicio 2

Sistema de detección y alerta de garaje

Objetivo: Implementar un sistema que detecte la presencia de un vehículo y controle la puerta y la luz del garaje según la distancia medida.
Escenario: Cargar garage en SimuPi.

Especificación del sistema

CondiciónAcción
Distancia < 80 cm (vehículo cerca)Encender luz (GPIO 24 = 1)
Distancia ≥ 80 cm (sin vehículo)Apagar luz (GPIO 24 = 0)
Distancia < 30 cm (demasiado cerca)Abrir puerta (GPIO 22 = 1) y enviar alerta al debug
Distancia ≥ 30 cmCerrar puerta (GPIO 22 = 0)

Flujo esperado en Node-RED

distance

zonas
→
gpio/out/22

Tareas

  1. Construir el flujo con un nodo switch que separe los tres rangos de distancia.
  2. Agregar un nodo function que construya un mensaje de alerta con timestamp cuando la distancia sea menor a 30 cm. Ejemplo:

Ejercicio 3

Detección y manejo de fallas de sensores

Objetivo: Diseñar un sistema robusto que detecte cuando un sensor deja de funcionar correctamente y active una alerta, diferenciando entre falla tipo stuck (valor congelado) y offline (sin datos).
Escenario: Cargar greenhouse en SimuPi.

Tipos de falla a simular

TipoComportamientoCómo activarla
stuck El sensor sigue enviando mensajes MQTT, pero el valor nunca cambia POST /api/failure/temperature {"mode": "stuck"}
o desde la API REST en Node-RED
offline El sensor deja de publicar mensajes MQTT completamente POST /api/failure/temperature {"mode": "offline"}

Lógica de detección

Para detectar falla stuck:

// En un nodo function con contexto de flujo
var current = parseFloat(msg.payload);
var last = flow.get("lastTemp") || 0;
var sameCount = flow.get("sameCount") || 0;

if (Math.abs(current - last) < 0.01) {
    sameCount++;
} else {
    sameCount = 0;
}
flow.set("lastTemp", current);
flow.set("sameCount", sameCount);

if (sameCount > 10) {
    msg.payload = "ALERTA: sensor temperature posiblemente stuck";
    return msg;
}
return null;

Para detectar falla offline, usá un nodo trigger que se resetee con cada mensaje y dispare una alerta si no recibe datos en 10 segundos.

Tareas

  1. Construir el flujo de detección de falla tipo stuck para el sensor de temperatura.
  2. Agregar detección de falla tipo offline usando el nodo trigger.
  3. Cuando se detecte una falla, publicar un mensaje en el tópico MQTT alertas/sensores con el tipo de falla y el timestamp.
  4. Activar cada tipo de falla desde la API REST y verificar que las alertas se generan correctamente.
  5. Implementar la lógica para limpiar la falla ({"mode": "clear"}) y verificar que el sistema vuelve a la normalidad.
Reflexión
En sistemas IoT reales, la detección de fallas de sensores es crítica. ¿Qué impacto tendría una falla tipo stuck no detectada en el sistema de invernadero del Ejercicio 1? Describir el escenario en el informe.
Ejercicio 4 — Integrador

Diseño de escenario propio

Objetivo: Diseñar, configurar y documentar un escenario IoT propio que combine al menos dos sensores, un actuador controlado por lógica y un mecanismo de alerta.

Propuestas sugeridas (elegir una o proponer la propia)

PropuestaSensoresActuadores
Tanque de agua inteligenteNivel (triangle), temperatura (wave)Bomba de llenado, alarma de desborde
Sala de servidoresTemperatura (wave), consumo eléctrico (random)Ventilación extra, alertas de consumo
EstacionamientoDistancia (ramp), contador (sawtooth)Barrera, señal de ocupación
Sistema de riego agrícolaHumedad suelo (walk), temperatura (wave)Riego por zonas, bomba principal

Pasos para crear el escenario

  1. Abrir el editor de configuración en la UI de SimuPi (ícono de engranaje)
  2. Definir el JSON del escenario. Ejemplo: 
    {
  "inputs": [17, 18],
  "outputs": [22, 24],
  "aliases": {"22": "bomba", "24": "alarma"},
  "sensors": {
    "nivel": {
      "mode": "triangle", "min": 0, "max": 100,
      "interval": 1, "period": 120, "unit": "%"
    },
    "temperatura": {
      "mode": "wave", "min": 10, "max": 35,
      "interval": 2, "period": 90, "unit": "°C"
    }
  }
}
  3. Click en Guardar como escenario con un nombre identificatorio (ej. mi_tanque)
  4. Construir en Node-RED el flujo de control para el escenario diseñado

Requisitos mínimos del flujo Node-RED

  • Leer todos los sensores del escenario
  • Implementar al menos una regla de control (if/then) que active un GPIO output
  • Generar alertas (en debug o tópico MQTT propio) ante condiciones críticas
  • Incluir manejo de falla de al menos un sensor

Entregables del ejercicio 4

  • JSON del escenario SimuPi creado
  • JSON del flujo Node-RED exportado
  • Capturas de pantalla del dashboard SimuPi y Node-RED funcionando
  • Descripción de la lógica implementada (1 página máximo)
